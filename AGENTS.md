# verified

verified is the champäne of agents. It attempts to build a proven correct agent : https://chezdodds.dev/blog/verified-preregistration/.

It builds a modern agent harness oriented around safety and correctness. 

The project follows the traditional RFC process and this contains the record of design decisions in docs/rfcs.  

Prefer straightforward designs and delete accidental complexity rather than preserving it.

v controls **dispatch**: what runs, when, with whose approval, at most once, with exactly one recorded result. It does not control the filesystem or the OS. Tools act on the world best-effort and report honestly. Containment is a future sandbox `Env`. `PRINCIPLES.md` sets out what v upholds and what it doesn't, and the admission rule a new promise must pass. Read it before adding or changing any guarantee.

This repository is a Rust workspace. Each crate under `crates/` sits on a real architectural boundary:

- `verified-domain`: the domain types every other crate shares: ids (an actor's `ActorId`; `TurnId` and `TaskId` are seqs of the log), envelopes and addresses (`user`, `v`, an actor), records, outcomes (`Exit`: `Ok`, `Failed`, `NotStarted`, `Unknown`), tools and their classes (`Safe`, `Unsafe`, `Keyed`), a call's shape (tool, subject, and whether it starts a task, spawns a child or cancels a task), grants and rules, an actor's birth (`Born`), limits and the payload trait. It holds types and pure helpers, written inside `verus!{}` so the core's proofs can talk about them, and the call table (`named`), plain Rust outside `verus!{}` that pairs each record with the proposal it names.
- `verified-core`: the sans-io core (`decide`, `apply`, `recover`, `resume`), the mailbox (`mailbox`: envelopes delivered and not yet carried; a model call carries the batch at its head, a user's message alone or the run of other envelopes before it) and the rules matcher (`rules::grant`, the first rule that fits a call). It is pure, sync and written inside `verus!{}`, and `just verify` checks it with Verus. An actor is born once (`resume` records the shell's `Born`); envelopes land as `Delivered` and start a turn when the actor is idle, or wait for the running one's next step boundary; while a user's message waits, no call of the step waits for the user (each is denied, "the user steered"); a background call (`bash` in the background, `wake`) resolves at its start and runs on as a task, bound to the call that started it, whose `TaskEnded` is its notification; a `cancel` of a task is recorded on it, so it is signalled once; a stop always lands (the message limit bounds mail only), revokes everything and sends `stop` to every child (`StopSent`, a `Keyed` task); after a crash, `Safe` and `Keyed` calls rerun under their key only while their turn proceeds (under a cancel or a stop they resolve `Unknown`), and a stopped actor reruns only its stops. Every grant is the user's approval command or a rule in force (`RulesLoaded`); `decide` records a user's grant only on the user's approval command and a run's report only as it came (`honest`). The rules file is `.verified/v.toml`; the shell reads it (`rules_file`, through the `Env` seam) at every boot and before each user message, and records it when its text changes. With no file the one rule is `read: allow`.
- `verified-model`: the Stateright model of the core in an abstract world (`Harness`). BFS explores it over a small domain (`Bounded`, which also bounds the world's faults); trace mode (`Harness::trace`) takes its actions' ids and sizes from a trace, and `replay` walks a run's observations through it one state at a time (each observation names the actions it means, and every `always` property is checked on each state). It also holds α (`alpha`) for records, events and effects, the abstraction from any payload to the model's `Abstract`. Its `suite` holds the bounds every model check runs under, and `coverage` keys each step of the model small (a call's class, how far it got and how it resolved; a crash against a run's act; a few situations) for BFS's edges (`coverage::explore`) and a replay's steps alike. Its tests hold the model checks, their planted bugs, and the property test that the core commutes with α.
- `verified-wire`: the types the daemon and TUI share: commands (actors addressed by id; the actor list and task list replies), AI SDK UI chunks plus the actor data chunks (`data-envelope` when mail lands, `data-step-carries` when a step consumes it, `data-task-start` and `data-task-end`, turn start and end), the transcript fold (turns with the envelopes each step carried, the mail still queued, the tasks), SSE and Durable Streams.
- `verified-server`: the daemon. It holds the async shell, the seams (model, log, environment, clock, entropy), the actor registry and the HTTP routes. Actors are sessions: the registry (`daemon::Registry`) hosts one log per actor under `.verified/actors/`, rebuilds itself at boot, caps the actors (`ServerLimits::sessions`) and never awaits a session. A root actor the user makes is born `main`, offered every tool; a spawned child is born as its parent's `spawn` named it. The shell delivers envelopes (`ActorHandle::deliver`) and the user's messages alike, to an idle or a busy actor (a message to a busy actor steers its turn), answering only once the `Delivered` is durable. Calls are parsed at the model boundary (`payload::Boundary`: the actor's tools, and the Clock and Entropy that mint a timer's deadline and a child's id before `StepFinished` records them). A background `bash` runs as a task under `task_timeout`, a `wake` sleeps until its durable deadline, `tasks` lists the log's tasks, and `send`, `spawn` and stops are delivered between logs by `outbox` (each delivery its own task, its envelope id minted from the licensing record's seq, so a rerun lands once). Every run but a timer's has a deadline (`ServerLimits::deadline`) past which the shell reports `Expired` (B2). A full log fails stop (L3). The rules file `.verified/v.toml` is read through the `Env` seam (`rules_file`). The routes are what the TUI uses (`/actors` and `/actors/{id}/…`: the commands, the actor list with each actor's waiting approvals, its task list, and its stream as SSE from an offset); the projection maps records to chunks and folds the same log into an actor's summary and tasks. A web client gets the full Durable Streams protocol when it arrives.
- `verified-tui`: the terminal client, an Elm-style loop that follows one actor's stream: an actor tree on top (refreshed on a tick; Tab and Shift-Tab follow another actor, and approvals and Esc go to the one followed), a panel of its running tasks, and messages typed while a turn runs sent at once to steer it (queued until a step carries them).
- `verified-sim`: deterministic simulation tests on turmoil. Only this crate enables the `sim` feature. Every run is also replayed through `verified-model`: the ledger, with the shell's sim-only observations (`shim::observe`), is folded into the model's `Observed` facts, and a run the model cannot follow fails. The replay checks the offsets the TUI read and when; what it folded there is the invariant I6's to check. `just coverage A B` prints the coverage keys BFS reaches under the suite's bounds against those seeds `A..A+B` and the directed scenarios reach, each gap classified (over-approximation, fidelity gap, test gap). A directed scenario (`directed`) is a literal scenario that reaches a gap no seed does: a BFS witness written out as the user's turns and answers, with the one ordering no seed promises (two runs acting together, or an interrupt durable before a run starts) kept by a barrier (`Scenario::hold`). `directed::run` fails one whose replay misses its target.
- `verified-cli`: the one binary, `verified`, which runs the TUI or the daemon (`verified daemon`).

Add a crate only when the code has a new boundary of this kind; do not create speculative crates. Every crate must inherit workspace package metadata and lint configuration.

Nondeterminism enters through explicit seams: `clippy.toml` bans direct use of wall and monotonic time, randomness, the filesystem, environment variables, hash-ordered collections, and unannotated interior mutability. Pass these in as data or through a seam; when an exception is genuinely needed, use `#[expect(..., reason = "...")]`, never `#[allow]`.

Run `just ci` before committing changes. Keep local and CI validation on the same path.

The development environment uses Rust Glancer rather than rust-analyzer. Glancer requires the `rust-src` toolchain component and is provided by devenv as `rust-glancer`.

devenv also provides Verus (`nix/verus.nix`). Verus pins its own rustc, separate from `rust-toolchain.toml`, and only verification runs on that toolchain. To upgrade Verus, bump the release and its hashes in `nix/verus.nix`, the `vstd` pin in `Cargo.toml`, and the toolchain in `devenv.nix` together.
